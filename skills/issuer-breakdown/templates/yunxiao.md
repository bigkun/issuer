# Yunxiao Work Item Templates

Yunxiao Projex natively supports three work item types: **Requirement (Req)**, **Bug**, and **Task**, each with distinct field templates and description templates. Yunxiao also supports custom fields and description template configuration.

References:
- https://help.aliyun.com/zh/yunxiao/user-guide/work-item-template-management
- https://help.aliyun.com/zh/yunxiao/custom-configuration-for-project-collaboration

## issuer Frontmatter → Yunxiao API Mapping

Field conversion in adapter `createIssue()` (src/adapter/yunxiao/index.ts):

| issuer frontmatter | Yunxiao API Field              | Description                                                  |
|--------------------|--------------------------------|--------------------------------------------------------------|
| `title`            | `subject`                      | Work item title                                              |
| `body`             | `description`                  | Work item description (Markdown body, `formatType: MARKDOWN`)|
| `type`             | `workitemTypeId`               | Mapped via `workTypeToCategory()` to Req/Bug/Task, then lookup typeId |
| `priority`         | `customFieldValues[priorityFieldId]` | Auto-mapped for Bug type (ensurePriorityFieldMapping) |
| `severity`         | `customFieldValues[severityFieldId]` | Auto-mapped for Bug type (ensureSeverityFieldMapping) |
| `labels`           | —                              | Yunxiao has no native labels; written to description only    |
| `assigned_to`      | `assignedTo`                   | Auto-fetched current user (ensureAssignedTo)                 |
| (config) `owner`   | `spaceId`                      | Project space ID (from config.repo)                          |
| (config) `repo`    | `spaceId`                      | Same as above                                                |
| `platform_id`      | —                              | Written by sync after creation (Yunxiao workitem ID)         |
| `platform_url`     | —                              | Written by sync after creation                               |
| `status`           | —                              | Managed by Yunxiao workflow                                  |
| `created_at`       | —                              | Auto-generated by Yunxiao (gmtCreate)                        |
| `updated_at`       | —                              | Auto-generated by Yunxiao (gmtModified)                      |

### type → category Mapping (src/adapter/yunxiao/mapper.ts)

| issuer `type` | Yunxiao category | Note                                  |
|---------------|------------------|---------------------------------------|
| `bug`         | `Bug`            | Bug / Defect                          |
| `story`       | `Req`            | Requirement                           |
| `task`        | `Task`           | Task                                  |
| `epic`        | `Req`            | Yunxiao has no Epic category; mapped to Req |

### Bug Type Special Field Mapping

When creating a Bug type, the adapter automatically handles `severity` and `priority` via `customFieldValues`:

1. **severity field**: resolved via `ensureSeverityFieldMapping()`
   - Finds field with `identifier === 'severity'` or `name === '严重程度'`
   - Option mapping: `critical`(致命) → `high`(严重) → `medium`(一般) → `low`(建议)

2. **priority field**: resolved via `ensurePriorityFieldMapping()`
   - Finds field with `identifier === 'priority'` or `name === '优先级'`
   - Option mapping: `critical`(P0/紧急) → `high`(P1/高) → `medium`(P2/中) → `low`(P3/低)

> Note: `severity` and `priority` are **independent** fields; both must be set simultaneously.

## Requirement (Req)

### Field Mapping

| issuer frontmatter | Yunxiao Field       | Description             |
|--------------------|---------------------|-------------------------|
| `type: story`      | Work item type: Req | category = `Req`        |
| `title`            | Subject             | Required                |
| `priority`         | Priority            | P0-P3                   |
| `labels`           | —                   | Custom labels (in body) |
| `assigned_to`      | AssignedTo          | Alibaba Cloud PK        |

### Description Template (Markdown)

```markdown
## User Story

As a [role]
I want [feature/capability]
So that [business value/benefit]

## Background & Motivation

<!-- Describe the context: why this is needed, what business pain point it solves. -->

## Feature Description

<!-- Describe the scope, interaction flow, and key rules in detail. -->

### Core Flow

1. [Step 1: User navigates to page X]
2. [Step 2: User clicks button Y]
3. [Step 3: System executes logic Z]

### Key Rules

- [Rule 1: Under condition X, execute Y]
- [Rule 2: Exception handling logic]

## Acceptance Criteria (Given-When-Then)

**Scenario 1: [Scenario Name]**
- Given [precondition]
- When [action]
- Then [expected result]

**Scenario 2: [Scenario Name]**
- Given [precondition]
- When [action]
- Then [expected result]

**Scenario 3: [Exception Scenario Name]**
- Given [precondition]
- When [exception action]
- Then [system message / fallback behavior]

## Non-functional Requirements

- **Performance**: <!-- e.g. response time < 200ms -->
- **Security**: <!-- e.g. requires authentication -->
- **Compatibility**: <!-- e.g. support IE11 / mobile -->

## Effort Estimation

- Development: X person-days
- Testing: Y person-days

## References

- Parent requirement: <!-- link to parent requirement/theme -->
- Dependencies: <!-- link to prerequisite tasks -->
```

### Key Conventions

- ✅ Must use User Story format (As a / I want / So that)
- ✅ Acceptance criteria must use Given-When-Then format
- ✅ At least 3 acceptance scenarios (including 1 exception scenario)
- ✅ Effort estimation required
- ✅ Formal, complete sentence descriptions
- ✅ Non-functional requirements as needed

## Bug (Defect)

### Field Mapping

| issuer frontmatter | Yunxiao Field       | Description                        |
|--------------------|---------------------|------------------------------------|
| `type: bug`        | Work item type: Bug | category = `Bug`                   |
| `title`            | Subject             | Required                           |
| `priority`         | Priority            | P0-P3 (independent from severity)  |
| `severity`         | Severity            | Required, independent from priority|
| `labels`           | —                   | Custom labels (in body)            |
| `assigned_to`      | AssignedTo          | Alibaba Cloud PK                   |

### Severity Levels

| Level     | Meaning                                          |
|-----------|--------------------------------------------------|
| critical  | System crash, data loss, security vulnerability  |
| high      | Core feature broken, no workaround               |
| medium    | Feature impaired, workaround exists              |
| low       | Cosmetic issue, minor inconvenience              |

### Priority vs Severity

These are evaluated independently:
- **Priority**: How urgently it needs to be fixed (P0=immediate, P3=when time permits)
- **Severity**: How bad the impact is on users/system
- Example: Homepage typo → `priority: low, severity: low`; Database corruption → `priority: critical, severity: critical`

### Description Template (Markdown)

```markdown
## Environment

- **Version**: <!-- e.g. v2.1.0 -->
- **OS**: <!-- e.g. macOS 14.2 / Windows 11 -->
- **Browser**: <!-- e.g. Chrome 120 / Safari 17 -->
- **Related module**: <!-- e.g. User Authentication / Order System -->

## Reproduction Steps

1. [Step 1: Navigate to page X]
2. [Step 2: Perform action Y]
3. [Step 3: Enter data Z]
4. [Step 4: Error occurs — specific error message]

## Expected Behavior

<!-- What should happen under normal conditions. -->

## Actual Behavior

<!-- What actually happened. Include error messages, stack traces, screenshots. -->

## Impact Scope

- **Affected users**: <!-- e.g. All users / Admins only / Specific region -->
- **Frequency**: <!-- e.g. Always / Intermittent (30%) / Specific conditions only -->
- **Workaround**: <!-- If available, describe the workaround -->

## Root Cause (if known)

<!-- Analysis of likely root cause, reference code location. -->

## Attachments

<!-- Error screenshots, log files, database dumps, etc. -->
```

### Key Conventions

- ✅ Reproduction steps MUST be numbered and reproducible
- ✅ Must distinguish "Expected Behavior" from "Actual Behavior"
- ✅ `priority` and `severity` MUST both be set
- ✅ Must include environment details
- ✅ No effort estimation needed (bugs are fixed, not estimated)
- ✅ Impact scope must describe affected users and frequency
- ✅ If workaround exists, it must be noted

### Title Convention

- ✅ Title MUST describe the **problem**, not the solution
- ✅ Use noun phrases or problem statements
- ❌ Do NOT use action verbs like "Fix", "Resolve", "Repair" in the title

**Examples**:
- ✅ `"Homepage data fails to load"` (describes the problem)
- ❌ `"Fix homepage data loading issue"` (describes the solution)
- ✅ `"User login page shows blank screen"`
- ❌ `"Fix user login page blank screen issue"`
- ✅ `"Order submission returns 500 error"`
- ❌ `"Fix order submission 500 error"`

## Task

### Field Mapping

| issuer frontmatter | Yunxiao Field        | Description             |
|--------------------|----------------------|-------------------------|
| `type: task`       | Work item type: Task | category = `Task`       |
| `title`            | Subject              | Required                |
| `priority`         | Priority             | P0-P3                   |
| `labels`           | —                    | Custom labels (in body) |
| `assigned_to`      | AssignedTo           | Alibaba Cloud PK        |

### Description Template (Markdown)

```markdown
## Objective

<!-- What needs to be done and the expected outcome. -->

## Implementation Steps

1. [Step 1: e.g. Create database table schema]
2. [Step 2: e.g. Implement API endpoint]
3. [Step 3: e.g. Write unit tests]
4. [Step 4: e.g. Update API documentation]

## Technical Constraints

- [Constraint 1: e.g. Must use existing auth service]
- [Constraint 2: e.g. Backward compatible with v1 API]
- [Constraint 3: e.g. Performance requirement QPS ≥ 1000]

## Impact Scope

- **Affected modules**: <!-- e.g. Auth module / API Gateway -->
- **Affected APIs**: <!-- e.g. POST /api/v1/login -->
- **Database changes**: <!-- e.g. Add user_tokens table -->

## Testing Checklist

- [ ] Unit tests cover new logic
- [ ] Integration tests verify upstream/downstream
- [ ] Manual test for edge cases
- [ ] Performance test (if applicable)

## References

- Parent requirement: <!-- link to parent requirement -->
- Dependencies: <!-- link to prerequisite tasks -->
```

### Key Conventions

- ✅ Focus on "what to do" and "how to do it"; no User Story format needed
- ✅ Implementation steps must be numbered and actionable
- ✅ Must list technical constraints
- ✅ Testing checklist uses checkbox syntax
- ✅ Describe impact scope (affected modules, APIs, database changes)
- ✅ Link to parent requirement and dependencies

## Type Selection Guide

| Scenario                         | Type     | Rationale                                    |
|----------------------------------|----------|----------------------------------------------|
| New feature, new capability      | Req      | User-facing value delivery                   |
| System error, feature malfunction| Bug      | Fixing an existing feature                   |
| Technical refactoring, perf tuning, config | Task | Non-user-facing technical work      |
| Cross-iteration composite goal   | Theme    | Collection of requirements/tasks (Yunxiao "Theme" type) |

> **Yunxiao "Theme" type**: Yunxiao supports "Theme" work items for aggregating multiple requirements and tasks. issuer does not map this as a standalone type; it can be handled via `epic` type + custom fields.
