# Jira Issue Templates

Jira Cloud natively distinguishes **Story**, **Bug**, **Task**, and **Epic** as first-class issue types.
Sync is handled exclusively via the Atlassian Rovo MCP Server — no REST adapter or API token required.

References:
- https://support.atlassian.com/jira-software-cloud/docs/what-is-an-issue/
- https://support.atlassian.com/jira-software-cloud/docs/configure-issue-types-for-a-company-managed-project/
- https://support.atlassian.com/jira-software-cloud/docs/how-do-i-create-the-definition-of-done/

## issuer Frontmatter → Jira MCP Tool Mapping

Field conversion performed by the AI agent when calling the Atlassian Rovo MCP tool
(`createJiraIssue` / `create_jira_issue`):

| issuer frontmatter  | Jira MCP parameter | Notes                                                              |
|---------------------|--------------------|--------------------------------------------------------------------|
| `title`             | `summary`          | Issue title / summary                                              |
| `body`              | `description`      | Markdown body; Rovo MCP converts to ADF automatically             |
| `type`              | `issueType`        | Mapped: story→Story, bug→Bug, task→Task, epic→Epic                 |
| `priority`          | `priority`         | critical→Highest, high→High, medium→Medium, low→Low               |
| `severity`          | —                  | Bug only; written to description body (no native Jira field)      |
| `dependencies`      | —                  | Informational for AI agent only                                    |
| `labels`            | `labels`           | Array of strings, passed as-is                                     |
| (config) `repo`     | `projectKey`       | From `.issuer/config.yml` → `repo` field (e.g. `PROJ`)            |
| (config) `owner`    | —                  | Jira Cloud domain from `.issuer/config.yml` → `owner` field       |
| `platform_id`       | —                  | Written by agent after creation (e.g. `PROJ-101`)                  |
| `platform_url`      | —                  | Written by agent after creation (e.g. `https://co.atlassian.net/browse/PROJ-101`) |
| `status`            | —                  | Managed by Jira workflow; not set on creation                      |
| `created_at`        | —                  | Auto-generated by Jira                                             |
| `updated_at`        | —                  | Auto-generated by Jira                                             |

### issuer type → Jira issueType Mapping

| issuer `type` | Jira `issueType` | Notes                                               |
|---------------|------------------|-----------------------------------------------------|
| `bug`         | `Bug`            | Defect or system malfunction                        |
| `story`       | `Story`          | User-facing functional requirement                  |
| `task`        | `Task`           | Technical, operational, or infrastructure work      |
| `epic`        | `Epic`           | Large body of work spanning multiple sprints        |

### Priority Mapping

| issuer `priority` | Jira `priority` | Description                              |
|-------------------|-----------------|------------------------------------------|
| `critical`        | `Highest`       | Fix immediately, drop everything (P0)    |
| `high`            | `High`          | Fix in current sprint (P1)               |
| `medium`          | `Medium`        | Fix in next sprint (P2) — default        |
| `low`             | `Low`           | Fix when time permits (P3)               |

## Story (User Story / Feature)

User-facing functional requirements. Focuses on user value and verifiable acceptance conditions.

### Field Mapping

| issuer frontmatter | Jira Field         | Description                          |
|--------------------|--------------------|--------------------------------------|
| `type: story`      | `issueType: Story` | User-facing functional requirement   |
| `title`            | `summary`          | Short, noun-phrase, no verb prefix   |
| `priority`         | `priority`         | Default: `medium`                    |
| `labels`           | `labels`           | e.g. `["frontend", "auth"]`          |

### Title Convention

- ✅ Noun phrase describing the capability, e.g. `User login via phone number`
- ✅ Concise and business-readable — product managers browse the backlog by title
- ❌ Do NOT use developer-centric verb prefixes like `Implement`, `Add`, `Build`

**Examples**:
- ✅ `"User login via phone number"`
- ❌ `"Implement phone number login feature"`
- ✅ `"Third-party OAuth integration (Google, Apple)"`
- ❌ `"Add OAuth support for Google and Apple"`

### Description Template (Markdown)

```markdown
## User Story

As a [type of user, e.g. registered member]
I want to [action / capability, e.g. log in using my phone number]
So that [value / benefit, e.g. I can access my account without remembering a password]

---

## Acceptance Criteria

- [ ] **Scenario 1: Successful login**
  - Given the user is on the login page with a valid phone number
  - When the user enters the correct OTP received via SMS
  - Then the user is authenticated and redirected to the homepage
- [ ] **Scenario 2: Invalid OTP**
  - Given the user has requested an OTP
  - When the user enters an incorrect or expired OTP
  - Then an error message "Verification code is invalid" is displayed and the user remains on the login page
- [ ] **Scenario 3: Rate limiting**
  - Given the user has requested OTP 3 times within 10 minutes
  - When the user tries to request a new OTP
  - Then a "Too many requests, please try again later" message is shown

---

## Design & Mockups

- **Figma / Prototype**: <!-- Link to design file or specific Figma frame -->
- **Design Notes**: <!-- Any specific UI/UX constraints or guidelines -->

---

## Definition of Done (DoD)

- [ ] Code reviewed by at least one team member.
- [ ] Unit tests pass with ≥ 80% coverage for new logic.
- [ ] Verified on Staging environment.
- [ ] No regressions on existing auth flows.
```

### Key Conventions

- ✅ Must use the `As a / I want to / So that` User Story format
- ✅ Acceptance criteria MUST use checkbox syntax (`- [ ]`) so they render as interactive checklists in Jira Cloud
- ✅ Minimum 3 acceptance scenarios (including at least 1 edge case or error scenario)
- ✅ Include a link to design mockups when UI is involved
- ✅ Include a Definition of Done checklist
- ❌ No effort estimation required (Jira uses Story Points via separate estimation field)

## Bug (Defect)

Focuses on rapid reproducibility and triage efficiency. Minimises back-and-forth between reporter and developer.

### Field Mapping

| issuer frontmatter | Jira Field         | Description                              |
|--------------------|--------------------|------------------------------------------|
| `type: bug`        | `issueType: Bug`   | Defect or system malfunction             |
| `title`            | `summary`          | Describes the problem, NOT the fix       |
| `priority`         | `priority`         | How urgently to fix (P0–P3)              |
| `severity`         | description body   | Impact severity (no native Jira field)   |
| `labels`           | `labels`           | e.g. `["bug", "regression", "auth"]`     |

### Severity vs Priority

These are evaluated **independently**:

| Level      | `priority` (Urgency)            | `severity` (Impact)                           |
|------------|----------------------------------|-----------------------------------------------|
| `critical` | Fix immediately, drop everything | System crash, data loss, security breach      |
| `high`     | Fix in current sprint            | Core feature completely broken, no workaround |
| `medium`   | Fix in next sprint               | Feature impaired but workaround exists        |
| `low`      | Fix when time permits            | Cosmetic issue, minor UX inconvenience        |

**Example**: A homepage typo → `priority: low, severity: low`. A login crash → `priority: critical, severity: critical`.

### Description Template (Markdown)

```markdown
## Bug Description

<!-- A clear and concise statement of what the bug is. -->

---

## Environment

- **App Version / Build**: <!-- e.g. v2.3.1-build-490 -->
- **OS / Device**: <!-- e.g. iOS 17.4 / iPhone 15 Pro, or Windows 11 / Chrome 124 -->
- **Browser** (if web): <!-- e.g. Chrome 124, Safari 17.4, Firefox 125 -->
- **Related Module**: <!-- e.g. User Authentication, Order Checkout, Admin Panel -->
- **Impact Severity**: **<!-- critical | high | medium | low -->**

---

## Steps to Reproduce

1. Go to [specific URL or screen]
2. Click on [button / element name]
3. Enter [specific input data]
4. Observe the result

<!-- Be as precise as possible. Include exact input values if relevant. -->

---

## Expected Behavior

<!-- What should have happened under normal conditions. -->

---

## Actual Behavior

<!-- What actually happened. Include the exact error message, visual glitch, or unexpected response. -->

---

## Impact Scope

- **Affected users**: <!-- e.g. All users / Admin users only / Users in CN region -->
- **Frequency**: <!-- e.g. Always reproducible / Intermittent (~30%) / Specific conditions only -->
- **Workaround**: <!-- If a workaround exists, describe it here. Otherwise: "None." -->

---

## Logs & Attachments

<!-- Paste relevant error logs, stack traces, or link to screenshots/recordings. -->

```
<!-- Paste console output, server-side logs, or network error responses here -->
```
```

### Key Conventions

- ✅ Title MUST describe the **problem**, not the solution
- ✅ Use noun phrases or problem statements (e.g. `"Homepage data fails to load"`)
- ❌ Do NOT use action verbs like `"Fix"`, `"Resolve"`, `"Repair"` in the title
- ✅ Steps to Reproduce MUST be numbered and independently reproducible
- ✅ Clearly separate `Expected Behavior` from `Actual Behavior`
- ✅ Both `priority` and `severity` MUST be set in frontmatter
- ✅ Include environment details (version, OS, browser)
- ✅ Note workaround if one exists
- ❌ No effort estimation (bugs are fixed, not time-estimated)

**Title Examples**:
- ✅ `"Login page shows blank screen on Safari 17"`
- ❌ `"Fix login page blank screen issue"`
- ✅ `"Order submission returns HTTP 500 on checkout"`
- ❌ `"Fix order submission error"`

## Task (Technical Work)

Focuses on clear engineering deliverables, implementation steps, and architectural impact. Used for refactoring, infrastructure changes, migrations, and technical debt.

### Field Mapping

| issuer frontmatter | Jira Field         | Description                              |
|--------------------|--------------------|------------------------------------------|
| `type: task`       | `issueType: Task`  | Technical, operational, or admin work    |
| `title`            | `summary`          | Action verb + subject (concise)          |
| `priority`         | `priority`         | Default: `medium`                        |
| `labels`           | `labels`           | e.g. `["backend", "infra", "migration"]` |

### Title Convention

- ✅ Start with an action verb, e.g. `Migrate session storage to Redis`
- ✅ Precise and technical — developers should understand scope from the title alone
- ❌ Avoid vague titles like `"Redis stuff"` or `"Backend work"`

### Description Template (Markdown)

```markdown
## Objective

<!-- What needs to be done, why it is necessary, and what problem it solves.
     Provide enough context so any developer can understand without prior knowledge. -->

---

## Implementation Steps

- [ ] **Phase 1: Preparation**
  - [ ] [Step 1.1: e.g. Provision Redis instance in staging]
  - [ ] [Step 1.2: e.g. Configure environment variable REDIS_URL]
- [ ] **Phase 2: Implementation**
  - [ ] [Step 2.1: e.g. Integrate ioredis client library]
  - [ ] [Step 2.2: e.g. Implement RedisSessionStore adapter class]
  - [ ] [Step 2.3: e.g. Update session middleware to use new store]
- [ ] **Phase 3: Validation & Cleanup**
  - [ ] [Step 3.1: e.g. Verify session persistence across server restarts]
  - [ ] [Step 3.2: e.g. Remove deprecated in-memory session code]

---

## Technical Constraints & Dependencies

- **Affected modules**: <!-- e.g. `auth-service`, `api-gateway`, session middleware -->
- **Affected APIs**: <!-- e.g. `POST /api/v1/login`, `GET /api/v1/session` -->
- **Database / Infrastructure changes**: <!-- e.g. Add Redis cluster, no schema migrations -->
- **Dependencies / Blockers**: <!-- e.g. Requires PROJ-88 (Redis infrastructure) to be completed first -->
- **Breaking changes**: <!-- None / Yes — describe impact and migration path -->

---

## Testing Checklist

- [ ] Unit tests added/updated for new logic.
- [ ] Integration tests pass on the Staging environment.
- [ ] Manual smoke test performed on critical user paths.
- [ ] Performance test verified (if applicable — state target: e.g. p99 < 50ms).
- [ ] Documentation / ADR updated (if applicable).
```

### Key Conventions

- ✅ Objective section provides full context — any developer should be able to start without asking
- ✅ Implementation steps are grouped by phase and use checkbox syntax for progress tracking
- ✅ List all affected modules, APIs, and infrastructure changes
- ✅ Explicitly state dependencies and blockers with issue links
- ✅ Specify if there are breaking changes and how to handle them
- ✅ Testing checklist uses checkbox syntax (`- [ ]`)

## Epic (Large Feature / Initiative)

Represents a major initiative spanning multiple sprints. Acts as a strategic container for Stories, Tasks, and Bugs. Focuses on business goals, scope boundaries, and success metrics.

### Field Mapping

| issuer frontmatter | Jira Field         | Description                              |
|--------------------|--------------------|------------------------------------------|
| `type: epic`       | `issueType: Epic`  | Large body of work, multi-sprint         |
| `title`            | `summary`          | High-level capability name               |
| `priority`         | `priority`         | Default: `medium`                        |
| `labels`           | `labels`           | e.g. `["epic", "q2-2026"]`               |

### Description Template (Markdown)

```markdown
## Strategic Objective

<!-- One paragraph describing what this Epic delivers and what business goal or KPI it targets.
     e.g. "Deliver a unified authentication system supporting social login (Google, Apple, GitHub)
     to reduce registration friction and improve conversion by 15%." -->

---

## Scope Boundaries

### In Scope
- [ ] [Deliverable 1: e.g. Social login via Google OAuth 2.0]
- [ ] [Deliverable 2: e.g. Social login via Apple Sign-In]
- [ ] [Deliverable 3: e.g. Automated account linking by matching email]

### Out of Scope
- [Item 1: e.g. MFA / Two-factor authentication (deferred to v3)]
- [Item 2: e.g. Enterprise SSO / SAML (will be a separate Epic)]

<!-- Clearly marking out-of-scope items prevents scope creep during development. -->

---

## Milestones & Deliverables

- **Milestone 1: Core social auth infrastructure** (Target: <!-- YYYY-MM-DD -->)
  - OAuth client setup, database schema, login button UI components.
- **Milestone 2: Account linking** (Target: <!-- YYYY-MM-DD -->)
  - Account merge logic, conflict resolution UI, migration script.
- **Milestone 3: Rollout & monitoring** (Target: <!-- YYYY-MM-DD -->)
  - Staged rollout (5% → 25% → 100%), error monitoring dashboard.

---

## Success Metrics

- Signup conversion rate increases by **≥ 15%** within 30 days of launch.
- OAuth-related support tickets decrease by **≥ 40%**.
- Average login latency **< 300ms** (p95).

---

## Child Issues

<!-- List the Stories, Tasks, and Bugs that belong to this Epic.
     The agent will link them to this Epic via the Jira "Epic Link" or "Parent" field. -->
- [ ] Story: [title] — `[PROJ-xxx]`
- [ ] Story: [title] — `[PROJ-xxx]`
- [ ] Task:  [title] — `[PROJ-xxx]`
```

### Key Conventions

- ✅ Strategic Objective explains the "why" (business value / KPI)
- ✅ Scope Boundaries MUST explicitly list both In Scope and Out of Scope items (prevents scope creep)
- ✅ Define time-bound Milestones with target dates
- ✅ Include measurable Success Metrics (quantified KPIs, not vague goals)
- ✅ Epics should be broken down into leaf-level child issues before the sprint begins

## Type Selection Guide

| Scenario                                      | Jira Type | Rationale                                     |
|-----------------------------------------------|-----------|-----------------------------------------------|
| User-facing new feature or capability         | Story     | Delivers direct user value                    |
| System error, feature malfunction, regression | Bug       | Restores an existing feature to working state |
| Technical refactoring, infra, migration, debt | Task      | Non-user-facing engineering work              |
| Multi-sprint initiative, major feature set    | Epic      | Strategic container for multiple child issues |
