# GitLab Issue Templates

GitLab also has a single work item type — Issue — distinguished by labels. GitLab supports Markdown templates in the `.gitlab/issue_templates/` directory, and Work Item types (Issue / Epic / Task / OKR) since 17.10.

Reference: https://docs.gitlab.com/user/project/description_templates/

## issuer Frontmatter → GitLab API Mapping

Field conversion in adapter `taskToIssueInput()` (src/adapter/gitlab/mapper.ts):

| issuer frontmatter | GitLab API Field     | Description                                               |
|--------------------|----------------------|-----------------------------------------------------------|
| `title`            | `title`              | Issue title                                               |
| `body`             | `description`        | Issue description (Markdown body)                         |
| `labels`           | `labels`             | Preserved from original labels                            |
| `type`             | `labels` += `type:${type}`    | Auto-appended, e.g. `type:bug`                   |
| `priority`         | `labels` += `priority:${priority}` | Auto-appended, e.g. `priority:high` |
| `dependencies`     | —                    | Informational for AI agent only                           |
| `severity`         | —                    | No native GitLab severity; written to body only           |
| `platform_id`      | —                    | Written by sync after creation (GitLab issue iid)         |
| `platform_url`     | —                    | Written by sync after creation                            |
| `status`           | —                    | Managed by GitLab Issue state                             |
| `created_at`       | —                    | Auto-generated by GitLab                                  |
| `updated_at`       | —                    | Auto-generated by GitLab                                  |

GitLab API also supports the following optional fields (not currently mapped in adapter, extensible):

| GitLab API Field   | Type     | Description                |
|--------------------|----------|----------------------------|
| `assignee_ids`     | number[] | Assignees (user ID list)   |
| `milestone_id`     | number   | Milestone ID               |
| `confidential`     | boolean  | Whether the issue is confidential |
| `epic_id`          | number   | Associated Epic ID         |

## Bug Report

### Template: `.gitlab/issue_templates/Bug.md`

```markdown
## Summary

<!-- Summarize the bug encountered concisely. -->

## Steps to Reproduce

1. <!-- Step 1 -->
2. <!-- Step 2 -->
3. <!-- Step 3 -->

## Current Behavior

<!-- What actually happens. Include error messages, stack traces, or screenshots. -->

## Expected Behavior

<!-- What should happen instead. -->

## Environment

- **GitLab version**: <!-- e.g. 16.8 -->
- **OS / Browser**: <!-- e.g. macOS / Chrome 120 -->
- **Deployment**: <!-- Self-managed / GitLab.com -->

## Relevant Logs / Screenshots

<!-- Paste relevant log output in code blocks. Attach screenshots if helpful. -->

## Possible Fix

<!-- Optional: If you can, link to the line of code that might be responsible. -->

/label ~"type::bug" ~"status::triage"
```

### Key Conventions

- ✅ Title MUST describe the **problem**, not the solution
- ✅ Use noun phrases or problem statements (e.g. "Homepage data fails to load")
- ❌ Do NOT use action verbs like "Fix", "Resolve", "Repair" in the title
- Use GitLab quick actions (e.g. `/label`) in templates for auto-labeling
- Current vs Expected behavior clearly separated
- Include GitLab version and deployment type (important for self-managed)
- Reference code by linking to specific lines: `https://gitlab.com/org/repo/-/blob/main/file#L42`

## Feature Proposal

### Template: `.gitlab/issue_templates/Feature.md`

```markdown
## Problem Statement

<!-- What problem does this feature solve? Describe the current limitation. -->

## Proposed Solution

<!-- Describe the solution you'd like in detail. -->

## User Story

As a [role]
I want [feature/capability]
So that [benefit/value]

## Alternatives Considered

<!-- Describe any alternative solutions you've considered. -->

## Acceptance Criteria

- [ ] [Criterion 1]
- [ ] [Criterion 2]
- [ ] [Criterion 3]

## Technical Details

- **Affected components**: <!-- e.g. API, frontend, database -->
- **API changes**: <!-- Describe any new/changed endpoints -->
- **Database migrations**: <!-- Describe schema changes if any -->

## Testing Strategy

- Unit tests: <!-- What to test -->
- Integration tests: <!-- What to test -->
- Manual verification: <!-- What to verify -->

/label ~"type::feature" ~"status::triage"
```

### Key Conventions

- GitLab emphasizes technical details and testing strategy
- Include API changes and database migration details
- Testing strategy is a required section (GitLab culture)
- Use quick actions for auto-assignment: `/assign @username`, `/milestone %v2.0`

## Task / Chore

### Template: `.gitlab/issue_templates/Task.md`

```markdown
## Objective

<!-- What needs to be done and why. -->

## Implementation Plan

1. [Step 1]
2. [Step 2]
3. [Step 3]

## Technical Notes

- **Implementation details**: <!-- Describe approach -->
- **Dependencies**: <!-- Links to related issues -->
- **Breaking changes**: <!-- Yes/No + details -->

## Definition of Done

- [ ] Code implemented and self-reviewed
- [ ] Unit tests added
- [ ] Integration tests passing
- [ ] Documentation updated
- [ ] Code review approved

/label ~"type::maintenance" ~"status::triage"
```

### Key Conventions

- GitLab prefers "Definition of Done" over simple testing checklist
- Include implementation plan with numbered steps
- Reference related issues with cross-links: `#123`, `org/repo#456`

## Epic

> GitLab has native Epic support (group-level). This template is for issue-based epics.

### Template: `.gitlab/issue_templates/Epic.md`

```markdown
## Overview

<!-- High-level description and business goal. -->

## Sub-issues

- [ ] #<issue-number> — <title>
- [ ] #<issue-number> — <title>
- [ ] #<issue-number> — <title>

## Scope

### In Scope
- [Item 1]
- [Item 2]

### Out of Scope
- [Item 1]

## Timeline

- **Start**: <!-- YYYY-MM-DD -->
- **Target**: <!-- YYYY-MM-DD -->

/label ~"type::epic"
/epic <!-- Link to group-level epic if applicable -->
```

### Key Conventions

- GitLab has native group-level Epics; prefer those over issue-based epics
- Use `/epic` quick action to link to group epics
- Sub-issues tracked via cross-references

## GitLab-Specific: Quick Actions Reference

Quick actions can be embedded in templates for auto-population:

| Quick Action          | Description                          |
|-----------------------|--------------------------------------|
| `/label ~"foo"`       | Add label                            |
| `/assign @user`       | Assign to user                       |
| `/milestone %v2.0`   | Set milestone                        |
| `/estimate 3d`        | Set time estimate                    |
| `/weight 5`           | Set issue weight                     |
| `/epic &1`            | Link to group epic                   |
| `/duplicate #123`     | Mark as duplicate                    |
| `/relate #123`        | Create relation                      |
