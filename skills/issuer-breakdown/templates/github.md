# GitHub Issue Templates

GitHub has a single work item type — Issue — distinguished by `labels` (e.g. `type:bug`, `type:feature`).

The recommended approach is to place YAML form templates in the `.github/ISSUE_TEMPLATE/` directory.

Reference: https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms

## issuer Frontmatter → GitHub API Mapping

Field conversion in adapter `taskToIssueInput()` (src/adapter/github/mapper.ts):

| issuer frontmatter | GitHub API Field  | Description                                            |
|--------------------|-------------------|--------------------------------------------------------|
| `title`            | `title`           | Issue title                                            |
| `body`             | `body`            | Issue description (Markdown body)                      |
| `labels`           | `labels`          | Preserved from original labels                         |
| `type`             | `labels` += `type:${type}`  | Auto-appended, e.g. `type:bug`                |
| `priority`         | `labels` += `priority:${priority}` | Auto-appended, e.g. `priority:high` |
| `dependencies`     | —                 | Informational for AI agent only                        |
| `severity`         | —                 | No native GitHub severity; written to body only        |
| `platform_id`      | —                 | Written by sync after creation (GitHub issue number)   |
| `platform_url`     | —                 | Written by sync after creation                         |
| `status`           | —                 | Managed by GitHub Issue state                          |
| `created_at`       | —                 | Auto-generated by GitHub                               |
| `updated_at`       | —                 | Auto-generated by GitHub                               |

## Bug Report

### Frontmatter Mapping

| Field        | Value                      |
|--------------|----------------------------|
| `type`       | `bug`                      |
| `labels`     | `["bug", "triage"]`        |
| `title`      | `[Bug]: <short summary>`   |
| `priority`   | `medium` (default)         |
| `severity`   | `medium` (default)         |
| `dependencies` | `[]` (default)           |

### Body Template (Markdown)

```markdown
## Description

<!-- A clear and concise description of what the bug is. -->

## Steps to Reproduce

1. Go to '...'
2. Click on '...'
3. Scroll down to '...'
4. See error

## Expected Behavior

<!-- What you expected to happen. -->

## Actual Behavior

<!-- What actually happened. Include error messages, stack traces, or screenshots if applicable. -->

## Environment

- **OS**: <!-- e.g. macOS 14.2, Windows 11, Ubuntu 22.04 -->
- **Browser**: <!-- e.g. Chrome 120, Firefox 121 -->
- **Version**: <!-- e.g. v2.1.0 -->

## Logs / Screenshots

<!-- Paste relevant log output or attach screenshots. -->

## Possible Root Cause

<!-- Optional: If you have an idea what might be causing this. -->
```

### Key Conventions

- ✅ Title prefix: `[Bug]:` for quick scanning
- ✅ Title MUST describe the **problem**, not the solution (e.g. `[Bug]: Homepage data fails to load`, NOT `[Bug]: Fix homepage data loading issue`)
- ✅ Steps to Reproduce MUST be numbered and reproducible
- ✅ Clearly separate Expected vs Actual behavior
- ✅ Always include Environment section (OS/Browser/Version)
- ✅ Use code blocks (```) for log output
- ✅ Add `priority` and `severity` labels if the project uses them

## Feature Request

### Frontmatter Mapping

| Field        | Value                           |
|--------------|---------------------------------|
| `type`       | `story`                         |
| `labels`     | `["enhancement", "triage"]`     |
| `title`      | `[Feature]: <short summary>`    |
| `priority`   | `medium` (default)              |
| `dependencies` | `[]` (default)                |

### Body Template (Markdown)

```markdown
## User Story

As a [role]
I want [feature/capability]
So that [benefit/value]

## Problem Statement

<!-- Describe the problem or limitation that this feature would solve. -->

## Proposed Solution

<!-- Describe the solution you'd like. Be as specific as possible. -->

## Alternatives Considered

<!-- Describe any alternative solutions or features you've considered. -->

## Acceptance Criteria

- [ ] [Criterion 1]
- [ ] [Criterion 2]
- [ ] [Criterion 3]

## Additional Context

<!-- Add any other context, mockups, or screenshots about the feature request. -->
```

### Key Conventions

- Start with User Story format (As a / I want / So that)
- Clearly state the problem before proposing a solution
- Acceptance Criteria MUST use checkbox syntax (`- [ ]`)
- Minimum 3 acceptance criteria
- Mention alternatives considered to show thoroughness

## Task / Chore

### Frontmatter Mapping

| Field        | Value                          |
|--------------|--------------------------------|
| `type`       | `task`                         |
| `labels`     | `["chore", "triage"]`          |
| `title`      | `[Task]: <short summary>`      |
| `priority`   | `medium` (default)             |
| `dependencies` | `[]` (default)               |

### Body Template (Markdown)

```markdown
## Objective

<!-- What needs to be done and why. -->

## Implementation Steps

1. [Step 1]
2. [Step 2]
3. [Step 3]

## Technical Details

- **Affected components**: <!-- e.g. auth module, API layer -->
- **Dependencies**: <!-- e.g. requires #123 to be merged first -->
- **Breaking changes**: <!-- Yes/No, and details if yes -->

## Testing Checklist

- [ ] Unit tests added/updated
- [ ] Integration tests verified
- [ ] Manual testing performed
- [ ] Documentation updated (if applicable)
```

### Key Conventions

- Focus on WHAT needs to be done, not business narrative
- Numbered implementation steps for clarity
- Always list affected components and dependencies
- Testing checklist ensures quality gate

## Epic

### Frontmatter Mapping

| Field        | Value                          |
|--------------|--------------------------------|
| `type`       | `epic`                         |
| `labels`     | `["epic"]`                     |
| `title`      | `[Epic]: <short summary>`      |
| `priority`   | `medium` (default)             |
| `dependencies` | `[]` (default)               |

### Body Template (Markdown)

```markdown
## Overview

<!-- High-level description of the epic and its business goal. -->

## User Stories / Sub-issues

- [ ] #<issue-number> — <story title>
- [ ] #<issue-number> — <story title>
- [ ] #<issue-number> — <story title>

## Scope

### In Scope
- [Item 1]
- [Item 2]

### Out of Scope
- [Item 1]
- [Item 2]

## Timeline

- **Start date**: <!-- YYYY-MM-DD -->
- **Target completion**: <!-- YYYY-MM-DD -->

## Success Metrics

- [Metric 1]
- [Metric 2]
```

### Key Conventions

- Epics aggregate multiple sub-issues (linked via `#number`)
- Define clear scope boundaries (In Scope / Out of Scope)
- Include timeline and success metrics
- Epics should be broken down into leaf-level issues before development starts
