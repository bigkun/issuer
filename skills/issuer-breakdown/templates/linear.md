# Linear Issue Templates

Linear natively supports highly structured issues and leverages lightweight properties (Priority, Labels, Assignee, Project, Cycle) to keep engineering teams fast and aligned.
Sync is handled via the Linear MCP Server (`https://mcp.linear.app/mcp`), which automatically converts Markdown descriptions.

References:
- https://linear.app/docs/issues
- https://linear.app/docs/mcp
- https://linear.app/docs/templates

## issuer Frontmatter → Linear MCP Tool Mapping

Field conversion performed by the AI agent when calling the Linear MCP tools (`create_issue` / `update_issue`):

| issuer frontmatter  | Linear MCP parameter | Notes                                                              |
|---------------------|--------------------|--------------------------------------------------------------------|
| `title`             | `title`            | Issue title / summary                                              |
| `body`              | `description`      | Markdown body; Linear renders Markdown beautifully                 |
| `type`              | `issueType / labels`| Story $\rightarrow$ Label: `story` / `Feature`, Bug $\rightarrow$ Label: `bug`, Task $\rightarrow$ Label: `task` |
| `priority`          | `priority`         | critical $\rightarrow$ Urgent (1), high $\rightarrow$ High (2), medium $\rightarrow$ Normal (3), low $\rightarrow$ Low (4) |
| `severity`          | —                  | Bug only; written to description body (no native Linear field)      |
| `dependencies`      | —                  | Informational for AI agent only                                    |
| `labels`            | `labels` / `labelIds` | Array of strings or IDs, passed as-is                           |
| (config) `repo`     | `teamId`           | From `.issuer/config.yml` $\rightarrow$ `repo` field (e.g. `ENG`) |
| (config) `owner`    | —                  | Linear Workspace Name from `.issuer/config.yml` $\rightarrow$ `owner` field |
| `platform_id`       | —                  | Written by agent after creation (e.g. `ENG-101`)                  |
| `platform_url`      | —                  | Written by agent after creation (e.g. `https://linear.app/workspace/issue/ENG-101`) |
| `status`            | `stateId`          | Managed by Linear workflow state                                   |
| `created_at`        | —                  | Auto-generated by Linear                                           |
| `updated_at`        | —                  | Auto-generated by Linear                                           |

### issuer Type $\rightarrow$ Linear Labels Mapping

| issuer `type` | Linear `Labels` | Description                                          |
|---------------|-----------------|------------------------------------------------------|
| `bug`         | `Bug`           | Defect or system malfunction                         |
| `story`       | `Feature`       | User-facing functional requirement                   |
| `task`        | `Task` / `Chore`| Technical, operational, or infrastructure work       |
| `epic`        | `Project` / `Epic`| Large body of work spanning multiple cycles        |

### Priority Mapping

| issuer `priority` | Linear `priority` | Level | Description                              |
|-------------------|-------------------|-------|------------------------------------------|
| `critical`        | `Urgent`          | 1     | Fix immediately, drop everything (P0)    |
| `high`            | `High`            | 2     | Fix in current cycle (P1)                |
| `medium`          | `Normal`          | 3     | Fix in next cycle (P2) — default         |
| `low`             | `Low`             | 4     | Fix when time permits (P3)               |

## Story (User Story / Feature)

User-facing functional requirements. Focuses on user value and verifiable acceptance conditions.

### Field Mapping

| issuer frontmatter | Linear Field       | Description                          |
|--------------------|--------------------|--------------------------------------|
| `type: story`      | Label: `Feature`   | User-facing functional requirement   |
| `title`            | `title`            | Short, noun-phrase, no verb prefix   |
| `priority`         | `priority`         | Default: `Normal` (3)                |
| `labels`           | `labels`           | e.g. `["frontend", "auth"]`          |

### Title Convention

- ✅ Noun phrase describing the capability, e.g. `User login via phone number`
- ✅ Concise and product-readable
- ❌ Do NOT use developer-centric verb prefixes like `Implement`, `Add`, `Build`

**Examples**:
- ✅ `"User login via phone number"`
- ❌ `"Implement phone number login feature"`

### Description Template (Markdown)

```markdown
## User Story

As a [type of user, e.g. registered member]
I want to [action / capability, e.g. log in using my phone number]
So that [value / benefit, e.g. I can access my account without remembering a password]

---

## Problem & Solution

### The Problem
<!-- Describe the limitation or friction that currently exists. -->

### Proposed Solution
<!-- High-level summary of the solution from the user perspective. -->

---

## Acceptance Criteria

- [ ] **Scenario 1: Successful login**
  - Given the user is on the login page with a valid phone number
  - When the user enters the correct OTP received via SMS
  - Then the user is authenticated and redirected to the dashboard
- [ ] **Scenario 2: Invalid OTP**
  - Given the user has requested an OTP
  - When the user enters an incorrect or expired OTP
  - Then an error message "Verification code is invalid" is displayed and the user remains on the login page
- [ ] **Scenario 3: Rate limiting**
  - Given the user has requested OTP 3 times within 10 minutes
  - When the user tries to request a new OTP
  - Then a "Too many requests, please try again later" message is shown

---

- **Design Notes**: <!-- Any specific UI/UX constraints or guidelines -->

- [ ] Code reviewed by at least one team member.
```

## Bug (Defect)

Focuses on rapid reproducibility and triage efficiency. Minimises back-and-forth between reporter and developer.

### Field Mapping

| issuer frontmatter | Linear Field       | Description                              |
|--------------------|--------------------|------------------------------------------|
| `type: bug`        | Label: `Bug`       | Defect or system malfunction             |
| `title`            | `title`            | Describes the problem, NOT the fix       |
| `priority`         | `priority`         | How urgently to fix (Urgent–Low)         |
| `severity`         | description body   | Impact severity (no native Linear field) |
| `labels`           | `labels`           | e.g. `["bug", "regression", "auth"]`     |

### Severity vs Priority

These are evaluated **independently**:

| Level      | `priority` (Urgency)            | `severity` (Impact)                           |
|------------|----------------------------------|-----------------------------------------------|
| `critical` | Fix immediately, drop everything | System crash, data loss, security breach      |
| `high`     | Fix in current cycle             | Core feature completely broken, no workaround |
| `medium`   | Fix in next cycle                | Feature impaired but workaround exists        |
| `low`      | Fix when time permits            | Cosmetic issue, minor UX inconvenience        |

### Description Template (Markdown)

```markdown
## Bug Description

<!-- A clear and concise statement of what the bug is. -->

---

## Environment

- **App Version / Build**: <!-- e.g. v2.3.1-build-490 -->
- **OS / Device**: <!-- e.g. iOS 17.4 / iPhone 15 Pro, or Windows 11 / Chrome 124 -->
- **Browser** (if web): <!-- e.g. Chrome 124, Safari 17.4, Firefox 125 -->
- **Related Module**: <!-- e.g. User Authentication, Order Checkout, Admin Panel -->
- **Impact Severity**: **<!-- critical | high | medium | low -->**

---

## Steps to Reproduce

1. Go to [specific URL or screen]
2. Click on [button / element name]
3. Enter [specific input data]
4. Observe the result

---

## Expected Behavior

<!-- What should have happened under normal conditions. -->

---

## Actual Behavior

<!-- What actually happened. Include the exact error message, visual glitch, or unexpected response. -->

---

## Impact Scope

- **Affected users**: <!-- e.g. All users / Admin users only -->
- **Frequency**: <!-- e.g. Always reproducible / Intermittent (~30%) -->
- **Workaround**: <!-- If a workaround exists, describe it. Otherwise: "None." -->

---

## Logs & Attachments

```
<!-- Paste console output, server-side logs, or network error responses here -->

## Task (Technical Work)

Focuses on clear engineering deliverables, implementation steps, and architectural impact. Used for refactoring, infrastructure changes, migrations, and technical debt.

### Field Mapping

| issuer frontmatter | Linear Field       | Description                              |
|--------------------|--------------------|------------------------------------------|
| `type: task`       | Label: `Task`      | Technical, operational, or admin work    |
| `title`            | `title`            | Action verb + subject (concise)          |
| `priority`         | `priority`         | Default: `Normal` (3)                    |
| `labels`           | `labels`           | e.g. `["backend", "infra", "migration"]` |

### Title Convention

- ✅ Start with an action verb, e.g. `Migrate session storage to Redis`
- ✅ Precise and technical — developers should understand scope from the title alone
- ❌ Avoid vague titles like `"Redis stuff"` or `"Backend work"`

### Description Template (Markdown)

```markdown
## Objective

<!-- What needs to be done, why it is necessary, and what problem it solves. -->

---

## Implementation Steps

- [ ] **Phase 1: Preparation**
  - [ ] [Step 1.1: e.g. Provision Redis instance in staging]
  - [ ] [Step 1.2: e.g. Configure environment variable REDIS_URL]
- [ ] **Phase 2: Implementation**
  - [ ] [Step 2.1: e.g. Integrate ioredis client library]
  - [ ] [Step 2.2: e.g. Implement RedisSessionStore adapter class]
  - [ ] [Step 2.3: e.g. Update session middleware to use new store]
- [ ] **Phase 3: Validation & Cleanup**
  - [ ] [Step 3.1: e.g. Verify session persistence across server restarts]
  - [ ] [Step 3.2: e.g. Remove deprecated in-memory session code]

---

## Technical Constraints & Dependencies

- **Affected modules**: <!-- e.g. `auth-service`, `api-gateway` -->
- **Database / Infrastructure changes**: <!-- e.g. Add Redis cluster, no schema migrations -->
- **Dependencies / Blockers**: <!-- e.g. Requires team-12 (Redis infrastructure) first -->
- **Breaking changes**: <!-- None / Yes — describe impact and migration path -->

---

## Testing Checklist

- [ ] Unit tests added/updated for new logic.
- [ ] Integration tests pass on the Staging environment.
- [ ] Manual smoke test performed on critical user paths.
- [ ] Performance test verified (if applicable).
- [ ] Documentation / ADR updated (if applicable).
```

## Epic (Project)

Represents a major initiative spanning multiple cycles. In Linear, Epics are typically referred to as **Projects** or **Epics**.

### Field Mapping

| issuer frontmatter | Linear Field       | Description                              |
|--------------------|--------------------|------------------------------------------|
| `type: epic`       | Project / Epic     | Large body of work, multi-cycle          |
| `title`            | `title`            | High-level capability name               |
| `priority`         | `priority`         | Default: `Normal` (3)                    |
| `labels`           | `labels`           | e.g. `["epic", "q2-2026"]`               |

### Description Template (Markdown)

```markdown
## Strategic Objective

<!-- High-level description of what this Epic delivers and what business goal or KPI it targets. -->

---

## Scope Boundaries

### In Scope
- [ ] [Deliverable 1: e.g. Social login via Google OAuth 2.0]
- [ ] [Deliverable 2: e.g. Social login via Apple Sign-In]

### Out of Scope
- [Item 1: e.g. MFA / Two-factor authentication (deferred to next phase)]
- [Item 2: e.g. Enterprise SSO / SAML]

---

## Milestones & Deliverables

- **Milestone 1: Core social auth infrastructure** (Target: <!-- YYYY-MM-DD -->)
  - OAuth client setup, database schema, login button UI components.
- **Milestone 2: Account linking** (Target: <!-- YYYY-MM-DD -->)
  - Account merge logic, conflict resolution UI, migration script.

---

## Success Metrics

- Signup conversion rate increases by **≥ 15%** within 30 days of launch.
- Average login latency **< 300ms** (p95).

---
```
